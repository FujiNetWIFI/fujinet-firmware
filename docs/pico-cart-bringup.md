# Bringing up a pico cartridge

How to add a cartridge for a new console under `pico/`: what to copy, what to write, and what
`pico/common` already does. Read `CONTRIBUTING.md` first; its rules apply here too.

## Two shapes

- **A ROM window.** The cart sits where a ROM would, and the console only reads it. Both
  directions of the mailbox ride on reads: the console reads hotspot pages whose low address
  byte is the data, and the cart paints replies into the window it serves. Most carts are this
  shape. Start from [pico/template/](../pico/template/).
- **An I/O card.** The bus has writes and ports, so the card answers registers instead of
  painting a window. [pico/s100/](../pico/s100/) is the example: it takes common's FujiBus
  codec and USB device, but has its own link (`s100_link.c`) in place of `fujibus_usb.c`, and no
  mailbox. Start from it; steps 2, 7, 9 and 10 below still apply, and the rest are its own.

## The pieces you write

A ROM-window cart is the template with these parts replaced. Everything else comes from
`pico/common` (see [pico/common/](../pico/common/)).

| Part | In the template | What it holds |
|---|---|---|
| Board | `firmware/boards/` | the chip, the flash, `FUJI_SYS_CLOCK_KHZ` and, if it changes, `FUJI_VREG_VOLTAGE` |
| Bus loop | `tmpl_cart.[ch]` | the pin map, and core1's loop: sample, serve, hand hotspot reads to core0 |
| Mapper | `tmplmap.[ch]` | the size gate, the plan, the window layout, and the connector decode |
| Mailbox | `fuji_mailbox.h` | where in the window the status fields, reply slices and hotspot pages sit |
| Port | `fujinet.c` | the `fuji_port_ops_t` hooks: publishing a byte, receiving and staging a pushed image |
| Client | `firmware/baked/` | the console program the cart serves at power-on, normally CONFIG |
| MAME device | none | a slot device that drives the same mapper and mailbox code over TCP |

## 1. Copy the template

Copy `pico/template/` to `pico/<platform>/` and rename the `tmpl` prefix in file and symbol
names. Set `CART_BOARD`, `CART_ELF`, `CART_BAKE` and `cart_gen` in `build-cart.sh`, and the project name,
`USB_PRODUCT`, sources and `CORE1` entry in `firmware/CMakeLists.txt`. Keep `fujicart_firmware()`;
its options are listed at the top of `pico/common/cmake/fujicart.cmake`.

## 2. The board

`firmware/boards/<board>.{h,cmake}` names the chip and flash. New carts are RP2354B boards;
model the header on `fujitemplate_rp2354b.h`. Set the clock in the header, beside the reason the
bus loop needs it; `main.c` calls `fuji_clock_init()`. On an RP2350, turn the pad pulls off on
every bus pin (erratum RP2350-E9), as the template's `main.c` does.

## 3. The bus loop

core1 serves the bus and nothing else. It runs from SRAM, calls nothing out of line and takes
no function pointers; `checksram.py` checks this after every link for the `CORE1` entry and the
symbols listed after it (`CORE1_NO_CALLS` also forbids calls).

- A select that pulses once per access: the template's loop.
- A select held low across accesses, or no select at all: `pico/arcadia/`'s loop, which acts on
  a change of the whole address instead.
- A bus too fast to serve from a polled loop: let the console read an SRAM directly and keep
  only the banking on the RP, as `pico/atari-7800/` does with a PIO slot table; or hold each
  cycle with a wait line until core1 answers, as `pico/s100/` does in PIO.

Put the address-to-window decode in the mapper as a `static inline`, so core1 and the MAME
device share it, and record a hotspot read in the ring (`fuji_cart_note_read()`) rather than
acting on it.

## 4. The mailbox

`fuji_mailbox.h` includes `fuji_mailbox_proto.h` first and `fuji_mailbox_check.h` last; the check
`#error`s if a field moved from where `fujimail.c` expects it. Registers 0x00-0x13 are the
protocol's; a platform register goes at 0x14 or above and arrives in the port's `own_reg`. An
image carrying "FUJI" at `FN_R_CLAIM` keeps the mailbox live after it boots; any other image
ends it. The console client mirrors these offsets by hand.

## 5. The mapper

`<p>map.c` decides whether an image fits (the gate, at OPEN, before the ESP32 fetches it) and how
it lays out (the plan, at close). An OPEN may carry size 0, so the close plans on `got`, every
byte pushed, not on what fitted. Known images with a non-default board go in a CRC table:
`fuji_crc32()` and `fuji_crc_find()` in common, generated by a `tools/mkmapdb.py` built on
`pico/common/tools/softlist.py`. A `.cfg` sibling's `mapper=` reaches `rom_close` as `mapper`.

## 6. The port and core0 services

`fujinet.c` fills a `fuji_port_ops_t` and calls `fuji_port_init()`, which binds fujimail to the
USB link, BOOTSEL and the `.cfg` sibling. Take what else applies from common:

- `fuji_store.c` when an image can be larger than RAM: a RAM tier and a flash tier, sized by the
  cart's `fuji_store_cfg.h`. Its close reports how much it kept; refuse when `got` is more.
- `fuji_watchdog.c` when the console's power or clock should send the cart back to CONFIG.

## 7. The client

`build.sh` builds the console programs with the console's toolchain into `build/`.
`build-cart.sh`'s `cart_gen` packs the one served at power-on with `pico/common/tools/mkromh.py`,
which refuses a client of the wrong size or without its claim. `./build-cart.sh --bake` copies
it into `firmware/baked/`, so CI and the ESP32 build need no console toolchain.

## 8. The MAME device

The device serves the same window from the same mapper, and drives `fujimail.c` with
`pico/common/emu/fujitcp.c` as the link to a fujinet-pc. `pico/arcadia/emu/` is the smallest.
Its `apply.sh` sources `pico/common/emu/graft.lib.sh`:

- `graft` and `graft_common` copy the device, the cart's sources and common's into the tree;
- `graft_fujins` renames the shared symbols, so several carts can share one MAME binary;
- `graft_lua` lists every grafted file in `bus.lua`.

The driver and slot edits stay in the cart's `apply.sh`. A function added to a common module
goes in `pico/common/emu/fujins.syms` too; its host test fails otherwise. Test against a
fujinet-pc of your own, never a public server.

## 9. Tests

`firmware/host_test/Makefile` lists `TESTS`, each test's `_SRCS`, and includes
`pico/common/host_test/cart.mk`, which also compiles the MAME-shared sources as C++ (list the
others in `C_ONLY_SRCS`). Listing `test_fujimail` runs common's mailbox test against this cart's
map, configured by `fujimail_test.h`. Test the mapper and decode against what MAME's own
handlers do for the same image.

## 10. Wiring it in

- A build step in `.github/workflows/pico-carts.yml` (`./build-cart.sh --baked`); the host tests
  run without one.
- The cart in `CARTS` in `pico/tools/cmpfw.py`.
- A row in `pico/README.md`, and the cart's own `README.md` in the shape `CONTRIBUTING.md` gives.
- For a Fujiversal board that embeds the cart in the ESP32 build, the `pico_*` keys in its board
  ini; see `fujiversal-flashing.md`.
