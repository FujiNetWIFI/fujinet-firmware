# pico/atari-5200

FujiNet for the Atari 5200: an RP2354B cartridge that serves the console's 32K cart window from
its own SRAM, loads any image the ESP32-S3 pushes, hands it to the console's BIOS as at power-on,
and serves a mailbox the console reaches by reads alone.

## How it fits
- The edge has A0-A13, D0-D7 and one enable per 16K half, and no R/W and, on the 4-port console, no
  clock. core1 follows the address and serves each byte from the live view; a 74HCT541 opened by
  the enables alone drives the bus. A read with a side effect counts once its address has held,
  so address skew never triggers one.
- Console to cart is reads only: register `n = v` is a read of `$B500+n` then of `$B600+v`, a TX
  byte `b` a read of `$B700+b`. The reply and status are painted at `$B000` and `$B400`.
- A push lands straight in the view buffer core1 is not serving, inside MOUNT_IMAGE, and is
  planned and laid out there. The client arms the swap, clears the machine as a power-on leaves
  it and jumps to the cart's `JMP ($FFFC)` at `$B5F0`; the read of its last byte swaps the image
  in, and the console's own BIOS starts it.
- GAME: the image runs, the mailbox off. APP: an image with the claim keeps the arena over every
  bank. A power cycle (the 5200 has no reset line) brings CONFIG back.
- The ESP32 side is the `fujiversal-atari5200` board ([lib/bus/rs232/](../../lib/bus/rs232/) over
  USB CDC).

## Build
- `./build.sh` builds the clients into `build/` (cc65: ca65 and ld65). `./build-cart.sh` bakes a
  client (`build/config.bin` from fujinet-config `atari5200/` if present) into `build/gen` and
  builds the firmware; `--baked` builds from `firmware/baked/` alone, `--bake` refreshes it.
- `make -C firmware/host_test` runs the host tests; `A52_CORPUS=<dir>` also plans a corpus.
- `emu/apply.sh <mame>` grafts the device (`-cartslot fujinet`); a single-driver build is enough:
  `make SUBTARGET=a5200 SOURCES=src/mame/atari/atari400.cpp`, with `REGENIE=1` the first time.
  `./run.sh` runs a client; `IMAGE=` serves any image from power-on. Run throttled, the device
  takes transactions off the emulated CPU's thread, as core0 does, so a push shows its progress;
  the harnesses run `-nothrottle` and get them inside the read.
- `tools/abprep.py` then `tools/abrun.py`, `tools/tierb.py` and `tools/soak.py` (`--merge`) run the
  three tiers over a corpus, resumably, into `build/ab/` and `build/soak/`.

## Notes
- Every one of the 182 No-Intro images (181 carts and the BIOS dump) passed all three tiers in
  MAME: frame-equal to MAME's own cart on both BIOSes; RAM, SP, X and P equal to a power-on at the
  BIOS's first look; byte-exact over the network, in both observer modes. Both Star Trek images
  sit on a static screen under the scripted input, on MAME's cart too.
- MAME picks 2-chip boards by path only from a `.hsi` line, so the A side is always told its
  board. Three 16K prototypes run under neither mapping in MAME's boot test (Star Trek Alt, Black
  Belt Proto 1, the Pac-Man kiosk demo) and keep the tracer's verdict.
- `.car` type 7 is atari800's Bounty Bob file order (fixed 8K last); MAME reads type 7 in its own
  order, atari800's type 159.
- Pin 26's voltage, the interlock, whether the enables are PHI2-qualified, and the commit settle
  time are unmeasured; the board is a Rev0 schematic (fujinet-hardware
  `ATARI-5200/FujiNet-5200-Rev0`), not yet built. Everything here ran in host tests and MAME only.
- Super Cart images up to 128K are served; Bosconian's 512K is not.
