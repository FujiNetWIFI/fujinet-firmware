# `pico/o2/firmware` — the RP2040 cartridge

A fork of [aotta/PicoPAC](https://github.com/aotta/PicoPAC) with the FujiNet
mailbox added — see `PROVENANCE.md` for what is vendored, what is not, and the
licence position.

**It builds and links; it has never run on hardware.** There is no Odyssey 2 and
no cartridge board here yet, so everything below is verified by construction and
by the emulator, not by a console.

```sh
../build-cart.sh            # FujiNet build -> firmware/build/PicoPAC_cart.uf2
../build-cart.sh --stock    # stock PicoPAC, as a regression check
```

Upstream files sit flat at the root; everything FujiNet adds is under `src/`,
`include/` and `host_test/`, so an upstream merge stays a readable diff.

| File | Role |
|---|---|
| `include/fuji_mailbox.h` | the mailbox address map; single source of truth |
| `include/fujibus.h`, `src/fujibus.c` | SLIP + FujiBus codec, shared with the Intellivision cart |
| `include/o2map.h`, `src/o2map.c` | how a raw cart image maps into the program window |
| `src/fuji_cart.c` | core1's write ring, and painting the mailbox into `rom_table` |
| `src/fujibus_usb.c` | FujiBus over the USB CDC link to the ESP32-S3 |
| `src/fujinet.c` | the mailbox service and the DBC push receiver |
| `src/fujiboot.c` | loads the baked-in console client at power-up |
| `include/fujiconfigrom.h` | that client, generated by `../tools/mkromh.py` |
| `host_test/` | desktop gates for the codec and the mapper |

## How it hangs together

Reads cost the bus loop nothing. The mailbox is painted straight into
`rom_table[]`, so serving it is the same instruction that already serves ROM —
by the time core1 sees the read, the byte is ROM as far as it is concerned.

Writes are recorded by core1 into a ring and acted on by core0, so the bus loop
stays a poll. The console cannot start a second transaction before it sees
ACKSEQ, so the ring only ever has to hold one.

Booting a game is a **pointer swap**, not a copy. The image is laid into
`new_rom_table` at commit, and core1 flips `fuji_rom` when it sees the console
fetch the cartridge reset vector — because this cartridge cannot reset the
Odyssey 2 (there is no reset line on the connector), so the swap has to happen
on the restart the player initiates, and it has to be atomic against a running
console.

```sh
cd host_test
gcc -Wall -Wextra -I.. -I../include -o /tmp/test_fujibus test_fujibus.c ../src/fujibus.c && /tmp/test_fujibus
gcc -Wall -Wextra -I../include     -o /tmp/test_o2map   test_o2map.c   ../src/o2map.c   && /tmp/test_o2map
# and against real images:
/tmp/test_o2map ../../build/*.bin
```

## Still to come

- **Hardware.** Nothing here has met a console. The o2em model in `../emu/` is
  the reference this was ported from, and it has been exercised against a real
  `fujinet-pc-rs232` for a mailbox round trip, a network mount-and-boot and a
  full browse — but an emulator agreeing with itself is not a bring-up.
- **Console power sensing.** The ESP32-S3 is the USB host, so its VBUS powers
  this cartridge long before the console does; the Intellivision hit exactly
  this and needed an unbounded, USB-pumped wait on a console-power signal. There
  is no such signal wired here: PicoPAC consumes GP0-GP27, leaving only GP28/GP29
  on the purple clone, and pin D (+5 V) is not routed to either.

  `PROVENANCE.md`; aotta's grant does not and cannot cover them.
